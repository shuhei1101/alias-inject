# 要件

## 要望

alias-inject の既存の文書を `dev-docs.yaml` の `documents[]` に文書の種類ごとの行で載せ、タグを付けて dev-docs で配信する。

- 対象は `docs/` の公開ドキュメントの Markdown のページと、`dev/設計書/` の YAML の設計書にする
- 行の分け方
  - 公開ドキュメント: `type: markdown` の行に載せる
  - 設計書: 種類（`dev/テンプレート/{種類}.schema.yaml` を持つ種別）ごとに `type: yaml` の 1 行にし、`schema` にその種類の Schema を指す
  - 1 つのファイルを 2 つの行に載せない（既存の `flowchart` の行のページを含む）
- メタデータは行の `metadata`・`defaults[]` で持つ。管理用の YAML は置かない
  - 設計書の文書の名前は、設計書の `title` から取る
  - 行は `metadata.alias_type` を持たせない（alias-inject の照合の対象にしない）
- タグは #32 と同じく、knowledge の語彙（`docs/tags.yaml`）の共通のグループに合う語を付け、合う語が無い主題は未登録の候補として付ける
- dev-docs の develop のクローンで `dev-docs.yaml` を読み込み、設定のスキーマの違反と、各文書の Schema の検査の違反が 0 件であることを確かめる

`未確定`: 設計書が種類の Schema の検査を通らなかったときの扱い（決める段: ドキュメント修正）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | この PR で設計書を修正して検査を通す | 設計書を全種類そろえて配信できる | 設計書の修正が入り、見積もり（2 pt）に収まらない |
| B | 通らない種類の行を置かず、`## スコープ外` へ回して起票する | 配信の設定の変更だけに収まる | その種類はこの PR では配信されない |

推奨: B

設計書は ai-monitor の設計書の検証を通っているため、通らない原因は dev-docs 側の Schema の扱い（`$ref` の解決など）の可能性が高く、設定の変更とは別の Issue で扱うほうがよい。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 端末の設定（`~/.config/dev-docs/settings.yaml`）に alias-inject の配信元の行を追加し、手元で配信を確かめる | この Issue は配信元の設定だけを扱う | #33 |
| alias-inject のタグのマスター（`dev-docs.yaml` の `tags`）を置く | #32 と同じく、dev-docs はタグのマスターのファイルの書式を決めておらず、未登録の候補のタグで引ける | 予定なし |
| 各フォルダの `README.md`・`index.yaml` を配信する | `index.yaml` から生成した目次で、dev-docs は行と `nav` から画面のサイドバーを作る | 予定なし |
| `dev/テンプレート/` の Schema を文書として配信する | 設計書の行の `schema` から指す検査の定義で、読む文書ではない | 予定なし |
| `dev/pr/` の PR ドキュメントを配信する | 作業 PR ごとの記録で、マージした後は更新しない | 予定なし |
| `dev-docs.yaml` の `nav`（画面のタブとサイドバーの構成） | `nav` が無ければ dev-docs は行ごとにタブを作り、行を種類ごとに分ければ足りる | 予定なし |
