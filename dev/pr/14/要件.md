# 要件

## 要望

端末の設定（`~/.config/alias-inject/settings.yaml`）の照合の定義を、`sources[]` から共通の構造 `aliases[]`（`schemas/aliases.schema.yaml`）に置き換える。

- 端末の設定に、読むリポジトリの `dev-docs.yaml` のパスを並べる。プラグインはその `dev-docs.yaml` の `aliases[]` を読み、照合に使う
- 端末だけのエイリアスは、同じ構造の `aliases[]` を端末の設定にも書ける
- `aliases[]` の要素は `id`・`enabled`・`type`・`paths`・`fields`（`id`・`match`・`title`・`description` ほか `type` ごとの列）を使う。`enabled: false` の要素は照合に使わない
- 端末の設定の `aliases[]` と、読んだ `dev-docs.yaml` の `aliases[]` を `schemas/aliases.schema.yaml` で検証する。スキーマに合わない要素は照合から外し、理由を残す（今の `sources[]` の要素を外すときと同じ扱い）
- `dev-docs.yaml` の `aliases[].paths` の相対パスは、その `dev-docs.yaml` のフォルダ（リポジトリの直下）から解決する。端末の設定の `aliases[].paths` の相対パスは、今の `files` と同じく `global` は設定ファイルのフォルダ、`projects` は起動したプロジェクトの直下から解決する
- `dev-docs.yaml` は `aliases[]` だけを読み、他のキーは読まない。dev-docs のサーバーにも mdmark のコードにも依存しない
- 文脈に出す語は `fields.title` の列の値にし、無ければ `fields.match` の最初の値にする
- `sources[]` は読まない（v0.1.0 のリリース前のため、互換は持たない）
- `global` / `projects` と、`enabled`・`origins`・`max_items`・`max_chars`・`exclude`・`heading` は今のまま
- `dev-docs.yaml` も、今の YAML と同じく更新時刻が変わったときだけ読み直す

`未確定`: 読むリポジトリの並べ方（決める段: 単一ユースケース設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `global` と `projects[]` の要素に `repositories[]` を置き、要素を `{config: dev-docs.yaml のパス, enabled}` にする | dev-docs の端末の設定の `projects[].config`・`enabled` と同じ構造で、行を消さずに止められる | パスだけ並べるより書く量が多い |
| B | `global` と `projects[]` の要素に `dev_docs: [dev-docs.yaml のパス]` を並べる | 書く量が少ない | 一時的に止めるには行を消す |

推奨: A

D-87 と A-25 の dev-docs の端末の設定に構造を揃えると、利用者が 2 つの設定を同じ読み方で書ける。
`projects[]` の中の相対パスは起動したプロジェクトの直下から解決し、`config: dev-docs.yaml` で起動したリポジトリの定義を読める。

`未確定`: 文脈のソースごとのセクションの見出し（今の `label` は共通の構造に無い）（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `type` ごとの固定の名前（用語・文書・コマンド・URL）を見出しにし、同じ `type` の要素は 1 つのセクションにまとめる | 設定に見出しのキーが要らない | リポジトリごとの区別が見出しに出ない |
| B | `aliases[].id` を見出しにする | 要素ごとに分かれる | `terms` のような ID がモデルへの文脈にそのまま出る |

推奨: A

モデルに渡す文脈で必要なのは引用の種類で、どのリポジトリの定義かは語ごとの ID で足りる。

`未確定`: `doc` の `mcp`（共通の構造の `fields` に無い）の扱い（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | `mcp` を廃止し、`doc` は `description` と `title` だけを追加する | 共通の構造だけで閉じる | 文書を引く MCP の名前を文脈に出せない |
| B | `dev-docs.yaml` の `name` から `{name}-docs` を作って追加する | 設定を書かずに MCP の名前を出せる | `dev-docs.yaml` の `aliases[]` 以外のキーと dev-docs の命名に依存する |

推奨: A

`aliases[]` だけを読む要望と D-118 の依存の向きに沿う。
MCP の名前を出す要望が出たら、共通の構造の変更として alias-inject に Issue を立てる（D-120）。

`未確定`: 追加した語の記録のキー（今はソースの `label` と項目の ID の組）（決める段: インターフェース定義設計）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | 定義の出所（`dev-docs.yaml` のパスか端末の設定）と `aliases[].id` と項目の ID の組にする | 別のリポジトリが同じ `aliases[].id` を使っても重ならない | キーが長くなる |
| B | `aliases[].id` と項目の ID の組にする | 今と同じ粒度 | リポジトリをまたいで ID が重なると、片方の語を追加しない |

推奨: A

`aliases[].id` の一意は 1 つの設定の中でしか決まらないため。

`未確定`: スキーマでの検証の方法（決める段: モジュール構成設計。ライブラリを使うならライブラリ選定を挟む）

| 案 | 内容 | メリット | デメリット |
| --- | --- | --- | --- |
| A | JSON Schema の検証ライブラリを `hooks/vendor/` に同梱し、`schemas/aliases.schema.yaml` を読んで検証する | スキーマの変更がそのまま検証に効く | mod のランタイムでコード生成（`new Function`）を使うライブラリが動くかを確かめる必要がある |
| B | スキーマが使うキーワード（`type`・`enum`・`required`・`additionalProperties`・`minItems`・`minLength`・`allOf` の `if`/`then`・`$ref`）だけを解釈する検証を hooks モジュールに書き、`schemas/aliases.schema.yaml` を読んで検証する | 依存が増えない | 対応しないキーワードがスキーマに増えると検証が漏れる |

推奨: B

hooks モジュールは js-yaml 以外に依存を持たず、スキーマが使うキーワードは限られている。
対応しないキーワードがスキーマにあれば誤りとして返し、検証の漏れに気づけるようにする。

## スコープ外

| 項目 | 理由 | 対応予定 |
| --- | --- | --- |
| 引用の種類 skill・tool・path・env・avoid の追加と、`term` の `fields.avoid` を使った知らせ | 要望は最初の 4 種類を共通の構造で読むこと | [#12](https://github.com/shuhei1101/alias-inject/issues/12) |
| mdmark でのスキーマの取り込みと YAML のエイリアスの登録 | 他のリポジトリの後続 | [shuhei1101/mdmark#125](https://github.com/shuhei1101/mdmark/issues/125) |
| dev-docs でのスキーマの取り込みと `dev-docs.yaml` の `aliases[]` の検証 | 他のリポジトリの後続 | [shuhei1101/dev-docs#3](https://github.com/shuhei1101/dev-docs/issues/3) |
| `dev-docs.yaml` の `aliases[]` 以外のキー（`enabled`・`documents` など）を読む | 要望は `aliases[]` だけを読むこと。`dev-docs.yaml` の `enabled` は dev-docs が配信するかの値 | 予定なし |
